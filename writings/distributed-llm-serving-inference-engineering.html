Inference engineering is the art of keeping tokens moving

Get the GPUs. Bring up vLLM or SGLang. Add replicas. Route for cache locality. Share KV state when it pays. Put a gateway across heterogeneous fleets. That short checklist is not “just deployment”—it is a compact description of distributed LLM inference engineering.

01 / Definition

Yes. More precisely: distributed LLM serving.

Model training produces weights. Inference engineering turns those weights into a service with a latency distribution, throughput envelope, availability target, security boundary, and cost per useful output token. The work spans GPU topology, kernels, memory allocation, batching, admission control, cache placement, routing, networking, observability, and capacity planning.

The deceptively simple path—GPU → engine → replicas → cache-aware router → shared cache → fleet gateway—crosses three distinct control loops. The engine loop schedules tokens and KV pages inside one process. The node loop balances requests across local replicas while respecting GPU and cache affinity. The fleet loop chooses a compatible pool, region, accelerator class, and failure domain.

Installing vLLM is inference serving. Choosing tensor parallelism, measuring tail latency, designing cache ownership, draining replicas without losing sessions, and controlling cost under burst load is inference engineering.

02 / Capacity before YAML

The first scheduler is the hardware topology.

“Get the GPUs” is often the hardest step because a GPU is not a fungible integer. Capacity, memory bandwidth, interconnect, NUMA placement, power, cooling, driver compatibility, and failure domain determine which parallelism strategies are viable. Two GPUs separated by PCIe and a CPU socket are not equivalent to two GPUs connected by a high-bandwidth fabric.

Fit the model, then leave room for the service

HBM_required ≈ weights + KV_cache + activations + graph/workspace + allocator_headroom

For a dense model, weight memory is approximately parameter_count × bytes_per_parameter, plus quantization metadata. KV memory grows with concurrent live tokens. A useful first-order estimate for a conventional transformer is:

KV_bytes_per_token ≈ 2 × layers × kv_heads × head_dim × bytes_per_element

The factor of two is for keys and values. Grouped-query and multi-query attention reduce kv_heads; sliding-window, hybrid, or state-space layers change the shape again. Never size a fleet from model-file bytes alone. The “free” HBM after loading weights is the inventory from which active sequences, prefix-cache blocks, CUDA graphs, temporary buffers, and fragmentation must all be paid.

Parallelism is a topology decision

Parallelism trade space
ModeWhat it doesBest fitPrimary tax

Inventory nodes by accelerator SKU, HBM capacity, link topology, NIC bandwidth, NUMA socket, driver/runtime version, supported precision, and measured engine profile. Kubernetes device plugins expose devices, and Topology Manager can coordinate NUMA-aware placement, but labels do not erase physical asymmetry. Benchmark the exact placement you will operate.

03 / The engine

vLLM and SGLang are schedulers with a model attached.

A modern serving engine does much more than call forward(). It admits requests, tokenizes prompts, allocates paged KV blocks, forms continuous batches, performs chunked prefill, launches attention and matrix kernels, samples tokens, streams responses, handles cancellation, and recycles memory. Its central problem is packing unlike requests into shared GPU iterations without violating latency goals.

Prefill and decode stress different resources

Prefill processes many prompt tokens in parallel and tends toward compute-heavy matrix multiplication. Decode advances each sequence one token at a time, repeatedly reads model weights and KV state, and often becomes memory-bandwidth and launch-latency sensitive. Mixing them maximizes utilization until a giant prompt monopolizes an iteration and damages inter-token latency. Chunked prefill limits that interference; prefill/decode disaggregation goes further by assigning them to separate worker pools.

Diagram 2 — continuous batching turns requests into token work

Iteration t+1prefill A[512:1024] · decode B · decode C · decode Dchunked prefill

Start with one engine instance and pin versions: container digest, engine version, CUDA/ROCm runtime, driver, model revision, tokenizer revision, quantization format, attention backend, and launch flags. Run correctness tests before load tests. Validate stop tokens, structured output, tool calling, streaming cancellation, maximum context, LoRA behavior, and deterministic settings your API promises.

04 / One node, several replicas

A replica is an isolation boundary, not free throughput.

Multiple replicas on one node can isolate tenants, expose separate model variants, improve failure containment, and exploit GPUs that do not need to participate in one tensor-parallel group. But every replica duplicates weights and maintains its own scheduler queues and HBM-resident KV blocks. Splitting an eight-GPU node into four two-GPU replicas trades a larger shared batching domain for four independent failure and cache domains.

Replica design questions
GPU ownershipGive each replica an explicit, stable device set. Avoid accidental overlap and cross-NUMA CPU pinning.
Ports and healthSeparate liveness (“process exists”) from readiness (“model loaded, warmed, and accepting admission”).
Memory headroomLeave margin for workload variance, graphs, allocator fragmentation, and cache transfers—not only steady-state KV.
Warm-upExercise representative prompt/output buckets before advertising readiness; cold kernels and empty caches are real states.
DrainingStop new admissions, allow active streams to finish up to a deadline, then terminate. Never kill first and hope clients retry safely.

The basic capacity test is not “can four processes start?” It is whether the node sustains the required arrival process at the target TTFT and inter-token latency while one replica is draining or failed. Reserve failure headroom explicitly; otherwise high availability exists only while nothing is broken.

05 / Cache-aware routing

Round-robin destroys information you already paid to compute.

If many requests share a system prompt, retrieved document, codebase prefix, or conversation history, the engine can reuse KV blocks for the common prefix. Automatic prefix caching avoids recomputing attention for cached prompt blocks; it does not reduce decode work and it does not help when prompts share no exact token prefix.

A round-robin balancer scatters related requests across replicas. A cache-aware router instead estimates or observes which worker owns the longest reusable prefix, then balances that benefit against queueing. SGLang’s cache-aware policy illustrates the essential control rule: prefer prefix affinity while the fleet is balanced, but switch toward the shortest queue when load skew crosses absolute and relative thresholds.

choose worker i minimizing: α·queue_cost(i) + β·prefill_cost(not_cached_on_i) + γ·transfer_cost(i) + δ·risk(i)

The router needs a cache index. That index may be predictive—an approximate radix tree built from prior routing decisions—or observed from engine KV events. Predictive state is cheap but can become wrong after eviction, restart, out-of-band traffic, or failed requests. Observed state is more faithful but introduces event ordering, loss, replay, and recovery problems. In either case, the routing index is a hint. The engine remains the authority on whether a block actually exists.

Canonicalize before hashing

Prefix identity must include the model and tokenizer revision, adapter/LoRA identity, cache dtype, relevant multimodal inputs, and any engine-specific cache namespace. Even a whitespace or chat-template change can alter token IDs. Never let two incompatible model configurations share a cache key merely because their request text looks similar.

06 / Shared KV infrastructure

LMCache expands the reuse domain—but every hit still has a price.

Local HBM prefix caching is fastest and smallest in scope. A system such as LMCache can persist and move reusable KV state through host memory or remote storage so another engine instance can retrieve it. This converts cache reuse from a process-local optimization into a data-placement problem.

Diagram 4 — the KV hierarchy
L1 · GPU HBMactive sequences + hottest prefixeslowest latency / smallest scope
L2 · host DRAMevicted or prefetched KV near the GPUPCIe / CXL movement
L3 · remote cacheshared prefixes across replicasNIC + serialization + lookup
L4 · storagelarge, colder reusable statecapacity first

A remote hit is useful only when loading cached KV is cheaper than recomputing the prefix and does not evict more valuable active state. For a prefix of T tokens:

reuse wins when lookup + transfer(KV(T)) + install < prefill_compute(T) − opportunity_cost

The crossover depends on model architecture, prefix length, quantization, GPU generation, host path, NIC, storage backend, and current contention. Small prefixes may be faster to recompute. Large shared prefixes may justify remote retrieval, especially when prefill capacity is the bottleneck. Measure the break-even curve rather than assuming that a cache hit is inherently good.

“Shared cache” does not mean coherent HBM

Replicas do not suddenly see one transparent GPU cache. The connector externalizes blocks, metadata describes ownership and compatibility, the destination reserves pages, data moves, and the engine installs it. There are races with eviction, duplicate loads, partial transfers, and cancellation. Production design needs request IDs, checksums or integrity validation where appropriate, timeouts, backpressure, bounded retries, cache namespaces, and a safe recompute fallback.

Cache correctness rule

A miss may make the request slower. A wrong hit can make the answer wrong. Cache identity and invalidation belong in the correctness model, not only the performance model.

07 / The heterogeneous fleet

The gateway routes capabilities, not merely traffic.

Once replicas are spread across accelerator types, nodes, zones, or regions, one global queue is usually the wrong abstraction. Different pools have different supported precisions, context limits, tensor-parallel widths, throughput curves, cache contents, network distance, failure domains, and cost. The gateway should first filter for correctness, then optimize placement.

Two-stage placement
StageQuestionSignals
1 · eligibilityCan this pool serve the request correctly?Model/tokenizer revision, adapter, context length, modality, precision policy, region/compliance, tool/grammar support.
2 · scoringWhich eligible pool is best now?Predicted TTFT/ITL, queue tokens, cache affinity, transfer cost, health, failure budget, egress, and marginal cost.

Route to a pool, not directly to an individual GPU across a WAN. The global gateway makes coarse decisions—region, model version, hardware class, availability zone—while a pool-local router makes fast decisions using current queue and KV locality. This hierarchy limits control-plane fan-out and keeps high-frequency cache signals close to where they matter.

Heterogeneity also makes autoscaling non-linear. One H100-class replica and one slower GPU are not “two replicas.” Express capacity in workload-specific service rates: prefill tokens per second at a prompt distribution, decode tokens per second at a concurrency distribution, and SLO-compliant requests per second. A pool weight derived from unloaded peak TPS will route too much work to the wrong place.

08 / Operate the queue

Optimize the latency distribution, not GPU utilization.

Inference exposes at least four clocks: queue time, time to first token (TTFT), inter-token latency (ITL or TPOT), and end-to-end latency. Throughput is usually split into prompt and generation tokens per second. Goodput is the fraction of offered work completed inside the SLO; it is the metric that prevents a saturated system from congratulating itself for high GPU utilization while users wait.

TTFT = gateway + queue + cache_lookup/transfer + uncached_prefill + first_decode + network_stream
AdmissionBound concurrency or queued tokens by tenant and pool. Reject or shed early with retry guidance before queues become unbounded.
SchedulingTrack waiting prompt tokens, active decode sequences, expected output, preemption, and batch composition—not only request count.
CacheMeasure queried tokens, hit tokens, useful bytes loaded, transfer time, eviction, failed lookup, and recompute fallback.
HardwareObserve HBM occupancy, bandwidth proxies, SM activity, power/throttling, interconnect, NIC, CPU saturation, and NUMA traffic.

vLLM exposes Prometheus-compatible engine metrics including running/waiting requests, KV-cache usage, prefix-cache queries and hits, prompt/generation token counters, and latency histograms. Join those with router, gateway, GPU, host, and network telemetry under one request trace. Without a shared trace ID, “the GPU was fine” and “the API was slow” become two dashboards arguing with each other.

Autoscale on leading indicators

GPU utilization is a lagging and ambiguous signal. Prefer queued tokens, predicted service time, SLO goodput, cache working-set pressure, and sustained admission rate. Scale-up must include model download/load and warm-up delay. Scale-down must account for active streams and the cache value that disappears when a replica is drained.

09 / Failure semantics

Every optimization adds a new way to be partially wrong.

Failure matrix
FailureSymptomRequired behavior
Engine crashStreams break; router state claims dead KV exists.Fail readiness, remove endpoint, expire placement records, retry only if API semantics allow.
Router restartLost or stale cache index.Fall back to load routing; rebuild from events/snapshots before trusting affinity.
Remote cache slow“Hits” inflate TTFT and consume HBM reservations.Strict lookup/transfer deadlines, circuit breaker, recompute fallback.
Network partitionGateway sees partial fleet; cache metadata diverges.Fence unreachable pools, keep decisions local, reconcile after recovery.
Bad rolloutSame model name maps to incompatible cache state.Versioned namespaces; no cross-revision cache reuse; canary and rollback.
OverloadQueue time dominates; retries amplify arrival rate.Admission limits, bounded queues, retry budgets, load shedding, client backoff.

Streaming makes retries delicate: once a client has observed output, replay can duplicate tokens or tool calls. Gateways need explicit idempotency semantics and must distinguish “not admitted,” “admitted but no output observed,” and “partial stream delivered.” Exactly-once generation is generally not something a stateless retry policy can manufacture.

High availability also applies to the routers. Multiple cache-aware router replicas can independently learn different approximate trees, reducing locality or producing inconsistent choices. Decide whether router state is expendable, replicated, snapshotted, or rebuilt from worker events—and document the degraded policy during recovery.

10 / Measurement

A benchmark is a workload model with receipts.

Single-request tokens per second is a kernel demo, not a capacity plan. Replay a distribution of input lengths, output lengths, arrival times, shared-prefix ratios, session turns, tenants, and cancellation rates. Include cold start, warm engine/empty cache, warm local cache, warm remote cache, replica loss, cache outage, and rolling deployment.

The minimum experiment matrix

AxisRepresentative valuesWhy it matters
Arrivalclosed-loop concurrency; open-loop Poisson; burst traceClosed-loop tests hide overload by slowing the sender.
Promptshort, median, long, max; real histogramPrefill cost and KV footprint are length-dependent.
Outputshort answer, long generation, early stopDecode occupancy controls concurrency.
Reuse0%, 25%, 75% shared prefix; multi-turn sessionsSeparates router and cache value from engine baseline.
Topologyone replica, N replicas, one failed, cross-pool spillReveals locality fragmentation and failure headroom.

Report p50/p95/p99 TTFT and ITL, request and token throughput, SLO goodput, error and cancellation rates, cache hit tokens—not just hit requests—bytes transferred, prefill saved, queue depth, power, and cost. Sweep offered load past saturation. The knee of the latency curve is more operationally useful than the absolute maximum throughput.

Common benchmark trap

If every request uses the same prefix and arrives after the first has warmed the cache, you measured an upper bound on reuse—not production capacity. If every prompt is random, you measured a lower bound. Publish both and the trace-derived middle.

11 / Build sequence

Add complexity only after its counterfactual is measured.

  1. Write the contract. Specify model revisions, request limits, streaming behavior, TTFT/ITL targets, availability, regions, privacy, and cost ceiling.
  2. Characterize hardware. Record GPU/NIC/NUMA topology, supported precisions, model fit, power limits, and measured engine service curves.
  3. Prove one engine. Pin the stack, validate correctness, establish a no-cache baseline, and find the safe saturation knee.
  4. Add one-node replication. Isolate GPUs, define readiness and draining, then retest with a replica unavailable.
  5. Add cache-aware routing. Compare round-robin, least-load, sticky/session, and prefix-aware policies using controlled prefix overlap.
  6. Add shared KV only when justified. Measure lookup, transfer, installation, and recomputation across prefix lengths; set timeouts at the observed crossover.
  7. Introduce the fleet gateway. Separate eligibility from scoring, use pool-local routing, and encode model/cache compatibility in versioned capabilities.
  8. Close the control loop. Trace requests end to end; autoscale on queued work and goodput; rehearse cache, router, engine, node, zone, and rollout failures.
# The production question behind every layer:
if incremental_goodput_gain > complexity_cost + failure_risk + transfer_tax:
    keep_the_layer()
else:
    simplify()

This is why the original checklist is unmistakably inference engineering. The hard part is not standing up six named components. It is making their independent schedulers, caches, queues, failure detectors, and cost models behave like one service.
